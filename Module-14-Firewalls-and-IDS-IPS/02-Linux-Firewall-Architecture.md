# Module 14 – Lesson 02: Linux Firewall Architecture

## 1. Introduction

Linux firewall architecture describes how Linux receives, processes, filters, and forwards network packets.

Unlike a simple application that runs independently, Linux firewall filtering is closely integrated with the Linux kernel.

The main technology behind Linux firewall functionality is called **Netfilter**.

### Learning Objectives

By the end of this lesson, you should be able to:

- Explain Linux firewall architecture.
- Understand the role of Netfilter.
- Identify the main packet-processing hooks.
- Understand firewall tables and chains.
- Differentiate iptables and nftables.
- Trace how packets move through a Linux system.
- Inspect the firewall architecture on Kali Linux.

## 2. Understanding Netfilter

**Netfilter** is a framework built into the Linux kernel that provides networking and packet-processing capabilities.

It supports:

1. Packet filtering.
2. Network Address Translation (NAT).
3. Connection tracking.
4. Packet modification.
5. Network traffic control.

Netfilter provides the underlying mechanisms used by Linux firewall systems.

### Simple Analogy

Imagine a large airport.

- Netfilter is the airport's security infrastructure.
- Firewall rules are the security policies.
- Packets are passengers.
- Firewall chains are inspection checkpoints.

Every packet follows a processing path, and the configured rules determine what happens to it.

## 3. Linux Firewall Architecture

The relationship between Linux firewall components can be represented as follows:

```text
          NETWORK TRAFFIC
                 |
                 v
          LINUX NETWORK STACK
                 |
                 v
             NETFILTER
                 |
        +--------+--------+
        |                 |
        v                 v
     iptables          nftables
        |                 |
        +--------+--------+
                 |
                 v
           FIREWALL RULES
                 |
        +--------+--------+
        |        |        |
        v        v        v
      ACCEPT    DROP    REJECT
```

Important:

iptables and nftables are different rule-management interfaces. They can use Netfilter functionality, but their rule systems are not identical.

## 4. Netfilter Hooks

Netfilter provides several important packet-processing hooks.

A hook is a point in the Linux network stack where packet-processing rules can be applied.

The five traditional Netfilter hooks are:

### A. PREROUTING

Processes incoming packets before the routing decision.

It is commonly used for destination NAT.

### B. INPUT

Processes packets destined for the local Linux machine.

Example:

A remote computer attempts to connect to the SSH service running on your Kali VM.

### C. FORWARD

Processes packets passing through the Linux machine.

Example:

Your Linux system acts as a router between two networks.

### D. OUTPUT

Processes packets generated by the local Linux machine.

Example:

Your Kali VM sends a DNS request to a DNS server.

### E. POSTROUTING

Processes packets after the routing decision, before they leave the system.

It is commonly used for source NAT.

### Summary Table

| Hook | Purpose |
|---|---|
| PREROUTING | Before routing decision |
| INPUT | Traffic destined for the local machine |
| FORWARD | Traffic passing through the machine |
| OUTPUT | Traffic generated locally |
| POSTROUTING | After routing decision |

## 5. Understanding Packet Flow

Not every packet follows the same path.

### Scenario A: Incoming Packet to the Linux Machine

Suppose another computer sends an SSH connection request to your Kali VM.

The simplified path is:

```text
External Network
       |
       v
   PREROUTING
       |
       v
 Routing Decision
       |
       v
     INPUT
       |
       v
 Local Linux Service
```

The firewall can decide whether to permit or block the connection.

### Scenario B: Outgoing Packet

Suppose your Kali VM connects to a website.

```text
Local Application
       |
       v
     OUTPUT
       |
       v
 Routing Decision
       |
       v
   POSTROUTING
       |
       v
 External Network
```

### Scenario C: Forwarded Packet

Suppose Linux acts as a router.

```text
Incoming Network
       |
       v
   PREROUTING
       |
       v
 Routing Decision
       |
       v
    FORWARD
       |
       v
   POSTROUTING
       |
       v
Destination Network
```

Understanding these paths is essential when troubleshooting firewall rules.

## 6. Tables and Chains in iptables

iptables organizes rules using tables and chains.

### Main iptables Tables

#### A. Filter Table

Responsible for ordinary packet filtering.

Common chains:

- INPUT
- OUTPUT
- FORWARD

#### B. NAT Table

Used for Network Address Translation.

Common chains:

- PREROUTING
- OUTPUT
- POSTROUTING

#### C. Mangle Table

Used for specialised packet modification.

#### D. Raw Table

Used for operations involving connection tracking, including marking packets to bypass connection tracking.

#### E. Security Table

Provides security-related packet handling where supported by the kernel and configuration.

### Understanding Chains

A chain is an ordered collection of firewall rules.

When a packet reaches a chain, rules are evaluated according to their order.

If a rule matches, its configured target determines the next action.

Examples:

- ACCEPT
- DROP
- REJECT
- RETURN

---

## 7. Understanding nftables Architecture

nftables is the modern Linux packet-filtering framework designed to replace much of the older iptables infrastructure.

It uses three important concepts:

### Tables

A table is a container for chains and rules.

### Chains

A chain organizes rules and can be attached to a Netfilter hook.

### Rules

Rules define conditions and actions for processing packets.

Example structure:

```text
nftables
   |
   +-- Table: inet filter
           |
           +-- Chain: input
           |
           +-- Chain: output
           |
           +-- Chain: forward
```

The `inet` family can handle both IPv4 and IPv6 traffic.

## 8. Connection Tracking (Conntrack)

Connection tracking allows Linux to maintain information about network connections.

It helps identify whether packets belong to:

- NEW connections.
- ESTABLISHED connections.
- RELATED connections.
- INVALID connections.

### NEW

A packet is attempting to establish a new connection.

### ESTABLISHED

The packet belongs to a connection that has already been established.

### RELATED

The packet belongs to a connection related to an existing connection.

### INVALID

The packet cannot be associated with a valid tracked connection.

### Example

A computer initiates an HTTPS connection to a website.

A stateful firewall can allow the initial outgoing connection and recognise the returning traffic as part of that established connection.

This avoids having to create a separate broad inbound permission for every returning packet.

---

## 9. NAT and Linux Firewalls

**Network Address Translation (NAT)** modifies network address information in packets.

Common forms include:

### SNAT

Source Network Address Translation.

Changes the source IP address of outgoing packets.

### DNAT

Destination Network Address Translation.

Changes the destination IP address of incoming packets.

### MASQUERADE

A form of source NAT commonly used when the outgoing interface has a dynamically assigned IP address.

NAT is often used in:

- Home routers.
- Virtual machine networks.
- Enterprise networks.
- Internet gateway systems.

Important: NAT and firewall filtering are related but different functions. NAT does not automatically provide complete security.

---

## 10. iptables and nftables Comparison

| Feature | iptables | nftables |
|---|---|---|
| Purpose | Firewall rule management | Firewall rule management |
| Architecture | Traditional interface | Modern framework |
| Rule structure | Tables and chains | Tables, chains, rules |
| IPv4 and IPv6 | Separate tools historically | Unified `inet` family |
| Rule management | Separate commands | Unified syntax |
| Modern Linux use | Legacy and compatibility environments | Preferred modern framework |

Some Linux distributions provide iptables compatibility through an nftables backend.

Do not assume that every system uses the same backend.

## 11. Practical Lab: Inspect Linux Firewall Architecture

### Objective

Inspect your Kali VM's firewall architecture without changing its configuration.

Create your lesson directory:

```bash
mkdir -p ~/module14-lab/lesson02
cd ~/module14-lab/lesson02
```

### Step 1: Check Kernel Version

```bash
uname -r
```

The Linux kernel provides the underlying networking functionality.

### Step 2: Inspect nftables

```bash
sudo nft list tables
```

This displays configured nftables tables.

Next:

```bash
sudo nft list ruleset
```

This displays the complete visible nftables ruleset.

### Step 3: Inspect iptables

```bash
sudo iptables -L -n -v
```

This displays IPv4 filter chains and rules.

Inspect the NAT table:

```bash
sudo iptables -t nat -L -n -v
```

### Step 4: Check iptables Backend

```bash
iptables --version
```

Some systems display:

```text
iptables v... (nf_tables)
```

This indicates that the iptables command is using the nftables backend.

### Step 5: Inspect Connection Tracking

If the `conntrack` command is installed:

```bash
sudo conntrack -L
```

This displays tracked network connections.

If the command is unavailable, record that it is not installed. Do not install anything just for this exercise.

### Step 6: Inspect Firewall Services

```bash
systemctl status ufw --no-pager
```

Then:

```bash
systemctl status nftables --no-pager
```

A service being inactive does not necessarily mean that no firewall rules exist. Always inspect the actual ruleset as well.
