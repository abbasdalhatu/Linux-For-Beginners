# LAB 05: INBOUND AND OUTBOUND TRAFFIC CONTROL

## 1. Introduction

Network traffic moves in two primary directions: inbound and outbound.

A firewall can control both directions to protect a computer or network.

**Inbound traffic** enters your system from another device.

**Outbound traffic** leaves your system and travels to another device.

For example:

- When someone connects to your SSH server, that is inbound traffic.
- When your Kali machine downloads a package, that involves outbound traffic.
- When your browser requests a website, it sends outbound traffic and receives inbound response traffic.

Understanding these directions is important when designing firewall rules.

## 3. Understanding Inbound Traffic

Inbound traffic refers to packets arriving at your computer.

Examples include:

- SSH connections from administrators.
- HTTP requests from website visitors.
- HTTPS requests to a web server.
- DNS queries directed at a DNS server.

Inbound traffic is important because attackers may attempt to reach exposed services.

A firewall can restrict access to only the services that are required.

### Example

Imagine a Linux web server with:

- SSH on port 22.
- HTTP on port 80.
- HTTPS on port 443.

The administrator may permit HTTP and HTTPS from appropriate clients while restricting SSH to trusted administration addresses.

## 4. Understanding Outbound Traffic

Outbound traffic refers to packets generated by your computer and sent to other systems.

Examples include:

- Downloading software updates.
- Browsing websites.
- Sending DNS queries.
- Connecting to remote APIs.
- Synchronizing system time.

Controlling outbound traffic helps prevent unauthorized communication and can reduce the risk of data exfiltration.

### Example

An organization may restrict outbound connections from a database server so it can communicate only with approved services.

This reduces unnecessary network exposure.

## 5. Understanding Firewall Chains

Linux firewall frameworks use different chains or hooks to process traffic.

| Chain or Hook | Purpose |
|---|---|
| INPUT | Traffic destined for the local machine |
| OUTPUT | Traffic generated by the local machine |
| FORWARD | Traffic passing through the machine |

### INPUT

Example:

Another computer connects to your Kali SSH server.

The packet is intended for Kali itself.

Relevant chain: INPUT.

### OUTPUT

Example:

Kali requests a software package from a repository.

The request originates from Kali.

Relevant chain: OUTPUT.

### FORWARD

Example:

Your Linux machine acts as a router and passes traffic between two networks.

Relevant chain: FORWARD.

## 6. Source and Destination Addresses

Every IP packet contains addressing information.

### Source IP Address

Identifies the sender of the packet.

Example:

```text
192.168.56.10
```

### Destination IP Address

Identifies the intended recipient.

Example:

```text
192.168.56.20
```

### Example Traffic Record

```text
Source IP: 192.168.56.10
Destination IP: 192.168.56.20
Protocol: TCP
Destination Port: 22
Direction: Inbound to destination
```

This describes a connection attempt to an SSH service.

## 7. Understanding Source and Destination Ports

A source port is associated with the sending application's communication endpoint.

A destination port identifies the receiving service endpoint.

Example:

```text
Source IP: 192.168.56.10
Source Port: 51520

Destination IP: 192.168.56.20
Destination Port: 443

Protocol: TCP
```

The destination service is HTTPS.

Do not confuse source ports with destination ports. A client normally uses a temporary source port when connecting to a server's known service port.

## 8. Stateful Traffic Control

Stateful firewalls track connection information.

They commonly classify traffic as:

- NEW
- ESTABLISHED
- RELATED
- INVALID

For example:

1. Your computer initiates an HTTPS connection.
2. The firewall recognizes a new connection.
3. The remote server responds.
4. The firewall recognizes the response as part of the established connection.

This helps avoid treating every response packet as an unrelated incoming connection.

## 9. Practical Exercise 1: Inspect Network Addresses

Open Kali Linux.

Run:

```bash
ip addr
```

Identify your network interface and IP address.

Next:

```bash
ip route
```

Identify your default route.

Then:

```bash
hostname -I
```

This displays the IP addresses assigned to the machine.

Record the results.

## 10. Practical Exercise 2: Inspect Active Network Connections

Run:

```bash
ss -tun
```

This displays TCP and UDP sockets.

Next:

```bash
ss -tuna
```

This displays listening and non-listening TCP and UDP sockets.

Finally:

```bash
ss -tpn
```

This displays TCP connections and, where permitted, associated process information.

You may use sudo if process details are unavailable:

```bash
sudo ss -tpn
```

Record:

- Local addresses.
- Remote addresses.
- Connection states.
- Ports.
- Any identifiable applications.

An empty connection list is a valid observation.

## 11. Practical Exercise 3: Inspect Routing Information

Run:

```bash
ip route show
```

Study the output.

A route might look like:

```text
default via 192.168.1.1 dev eth0
```

This indicates that traffic without a more specific route can be sent through the listed gateway and interface.

Your actual interface name and addresses may differ.

Now run:

```bash
ip route get 1.1.1.1
```

This asks the routing system how it would route traffic toward the specified destination.

It does not send a packet to that destination.

Record the selected interface, gateway if shown, and source address.

## 12. Practical Exercise 4: Observe Traffic Locally

If `tcpdump` is already installed, check its availability:

```bash
command -v tcpdump
```

If available, inspect the available network interfaces:

```bash
ip -br addr
```

Choose your active interface.

You can inspect a small sample of local traffic with:

```bash
sudo timeout 10 tcpdump -ni INTERFACE -c 20
```

Replace `INTERFACE` with your actual interface name.

For example, if your interface is `eth0`:

```bash
sudo timeout 10 tcpdump -ni eth0 -c 20
```

This captures up to 20 packets for a maximum of 10 seconds.

If no packets are captured, that is acceptable.

**Privacy reminder:** Packet captures can contain sensitive metadata. Keep this exercise within your own Kali VM and do not share captures containing private information.

If tcpdump is unavailable, skip this exercise and record that it is not installed. Do not install additional tools just for this lab.

## 13. Practical Exercise 5: Design Inbound and Outbound Policies

Imagine you administer a Linux web server.

Design a policy using this table:

| Traffic | Direction | Proposed Policy |
|---|---|---|
| Public HTTPS requests | Inbound | Allow |
| Unnecessary Telnet connections | Inbound | Deny |
| Approved software updates | Outbound | Allow |
| Unauthorized external connections | Outbound | Restrict |
| Required DNS resolution | Outbound | Allow |
| Unnecessary service exposure | Inbound | Deny |

Consider the following questions:

1. Which services must be accessible?
2. Which destinations should the server contact?
3. Which traffic should be logged?
4. How will legitimate response traffic be handled?
5. How will administrators recover from an incorrect rule?

Do not implement this policy on your current VM.

## 15. Security Best Practices

When controlling inbound and outbound traffic:

1. Permit only necessary inbound services.
2. Restrict administrative access to trusted sources.
3. Monitor unexpected outbound connections.
4. Use stateful filtering where appropriate.
5. Apply least privilege.
6. Document firewall policies.
7. Monitor network activity.
8. Investigate suspicious destinations.
9. Maintain legitimate DNS and update access.
10. Test firewall changes in an isolated environment.
