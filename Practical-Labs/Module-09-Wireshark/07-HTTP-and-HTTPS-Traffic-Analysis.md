
# MODULE 09 – WIRESHARK AND NETWORK TRAFFIC ANALYSIS

# LESSON 07: HTTP AND HTTPS TRAFFIC ANALYSIS

## 1. Introduction

HTTP and HTTPS are application-layer protocols used for communication between web clients and web servers.

Whenever you open a website, your browser communicates with a web server using HTTP or HTTPS.

Understanding these protocols helps cybersecurity analysts:

- Investigate web communication.
- Troubleshoot website problems.
- Identify suspicious HTTP requests.
- Understand web server responses.
- Inspect TLS handshakes.
- Recognize encrypted traffic.
- Investigate web-based security incidents.

In this lesson, you will use Wireshark to inspect HTTP and HTTPS traffic generated by your own Kali VM.

## 2. What Is HTTP?

HTTP stands for Hypertext Transfer Protocol.

It is an application-layer protocol used to transfer resources between clients and servers.

Examples of HTTP resources include:

- HTML documents.
- Images.
- CSS files.
- JavaScript files.
- Text documents.
- API responses.

HTTP follows a request-response communication model.

### HTTP Communication

```text
CLIENT                         WEB SERVER
  |                                 |
  |---------- HTTP REQUEST -------->|
  |                                 |
  |<--------- HTTP RESPONSE --------|
  |                                 |
  |          RESOURCE               |
```

The client sends a request, and the server returns a response.

Traditional HTTP commonly uses TCP port 80.

## 3. What Is HTTPS?

HTTPS stands for Hypertext Transfer Protocol Secure.

It is HTTP communication protected by TLS (Transport Layer Security).

HTTPS provides:

- Encryption.
- Data integrity protection.
- Server authentication through certificates.
- Protection against many forms of network eavesdropping and modification.

HTTPS commonly uses TCP port 443.

HTTP/3 is different: it uses QUIC over UDP, commonly on port 443.

Important: HTTPS does not guarantee that a website is trustworthy. It protects the connection, not the honesty or safety of the website itself.

## 4. HTTP vs HTTPS

| Feature | HTTP | HTTPS |
|---|---|---|
| Full name | Hypertext Transfer Protocol | HTTP Secure |
| Common port | 80 | 443 |
| Encryption | No built-in transport encryption | TLS protection |
| Data visibility | Application content is generally readable | Application content is encrypted |
| Integrity protection | Not provided by HTTP itself | Provided by TLS |
| Authentication | No TLS certificate authentication | Server certificate authentication |

## 5. Understanding HTTP Requests

An HTTP request is a message sent by a client to a server.

A request commonly contains:

1. Request method.
2. Request target or path.
3. HTTP version.
4. Headers.
5. Optional message body.

Example:

```http
GET /index.html HTTP/1.1
Host: example.com
User-Agent: ExampleBrowser
Accept: text/html
```

This is an illustrative HTTP request.

### Important HTTP Methods

| Method | Purpose |
|---|---|
| GET | Retrieve a resource |
| POST | Submit data |
| PUT | Create or replace a resource |
| PATCH | Partially update a resource |
| DELETE | Request resource deletion |
| HEAD | Retrieve response headers without the normal response body |
| OPTIONS | Discover supported communication options |

A method alone does not determine whether an action is dangerous. Its meaning depends on the application and server configuration.

## 6. Understanding HTTP Response Codes

HTTP response codes indicate the result of a request.

### 1xx – Informational

The request is being processed.

### 2xx – Success

The request was successfully handled.

Examples:

- 200 OK.
- 201 Created.
- 204 No Content.

### 3xx – Redirection

The client may need to perform another request.

Examples:

- 301 Moved Permanently.
- 302 Found.
- 304 Not Modified.

### 4xx – Client Errors

The request could not be processed as submitted.

Examples:

- 400 Bad Request.
- 401 Unauthorized.
- 403 Forbidden.
- 404 Not Found.

### 5xx – Server Errors

The server encountered a problem.

Examples:

- 500 Internal Server Error.
- 502 Bad Gateway.
- 503 Service Unavailable.

## 7. HTTP Headers

HTTP headers provide additional information about requests and responses.

Examples include:

| Header | Purpose |
|---|---|
| Host | Identifies the requested host |
| User-Agent | Identifies client software |
| Accept | Indicates acceptable response formats |
| Content-Type | Identifies the message body format |
| Content-Length | Indicates body length |
| Authorization | Carries authentication credentials or tokens |
| Cookie | Sends stored cookie information |
| Set-Cookie | Requests that the client store a cookie |
| Cache-Control | Controls caching behaviour |

Some headers may contain sensitive information.

Never publish captures containing real passwords, session cookies, authentication tokens, or private user information.

## 8. Understanding TLS

TLS stands for Transport Layer Security.

TLS protects communication between clients and servers.

A simplified TLS handshake involves:

1. ClientHello.
2. ServerHello.
3. Certificate and authentication-related messages, depending on the TLS version and configuration.
4. Key establishment.
5. Secure application communication.

Modern TLS versions use different handshake details from older versions.

TLS 1.3 generally encrypts more of the handshake than earlier versions.

## 9. TLS Certificates

A TLS certificate helps authenticate a server.

Certificate information can include:

- Subject name.
- Subject Alternative Names (SANs).
- Issuer.
- Validity period.
- Public key information.
- Signature information.

A certificate is not proof that the website is harmless.

It helps establish the identity of the server according to the certificate validation process.

## 10. What Can Wireshark See in HTTPS?

Without authorized decryption keys, Wireshark generally cannot display HTTPS application content.

However, it may still reveal useful metadata, depending on the protocol and configuration:

- Source IP address.
- Destination IP address.
- Port numbers.
- Packet sizes.
- Timing information.
- TLS handshake information.
- Certificate information when visible.
- Connection establishment and termination.

Encrypted payloads should not be mistaken for readable HTTP messages.

Encrypted DNS, encrypted ClientHello, and other privacy technologies can reduce the metadata visible to network observers.

## 12. Practical Exercise 1: Create a Local HTTP Server

We will create a local web server that runs only on your Kali VM.

This provides a controlled environment for capturing HTTP traffic.

Step 1: Create a sample webpage.

```bash
echo "<h1>Wireshark HTTP Laboratory</h1>" > ~/practical-labs/module09/lab07/www/index.html
```

Step 2: Enter the web directory.

```bash
cd ~/practical-labs/module09/lab07/www
```

Step 3: Start the Python HTTP server.

```bash
python3 -m http.server 8000 --bind 127.0.0.1
```

The server is now listening on:

```text
http://127.0.0.1:8000
```

The server is bound to loopback, so it is accessible only from the same machine.

Keep this terminal open.

## 13. Practical Exercise 2: Generate HTTP Traffic

Open a second Kali terminal.

Request the local webpage:

```bash
curl http://127.0.0.1:8000
```

You should receive the HTML content.

Inspect the HTTP response headers:

```bash
curl -I http://127.0.0.1:8000
```

Test a missing page:

```bash
curl -I http://127.0.0.1:8000/missing.html
```

The server should normally return a 404 response for the missing page.

These requests generate HTTP traffic between local processes.


Step 4: Return to your second terminal and execute:




- HTTP method.
- Request URI.

- Host header.

## 15. Practical Exercise 4: Analyze HTTP Filters

Useful Wireshark display filters include:

Show HTTP traffic:

```text
http
```

Show HTTP GET requests:

```text
http.request.method == "GET"
```

Show HTTP POST requests:

```text
http.request.method == "POST"
```

Show HTTP responses:

```text
http.response
```

Show successful HTTP 200 responses:

```text
http.response.code == 200
```

Show HTTP 404 responses:

```text
http.response.code == 404
```

Show HTTP 500 responses:

```text
http.response.code == 500
```

Show HTTP traffic on port 8000:

```text
tcp.port == 8000
```

Show HTTP requests for a particular host:

```text
http.host == "127.0.0.1"
```

If a filter returns no results, verify that the capture contains the relevant packets and that Wireshark has decoded the protocol.

## 16. Practical Exercise 5: Follow an HTTP Stream

Wireshark can reconstruct a TCP conversation.

Step 1: Select one of the HTTP packets.

Step 2: Right-click the packet.

Step 3: Choose:

```text
Follow → TCP Stream
```

Step 4: Inspect the reconstructed communication.

Look for:

- GET request.
- HTTP headers.
- Server response.
- Response code.
- Returned HTML.

This demonstrates why unencrypted HTTP traffic can expose application content to network observers who can access the traffic.

Only perform this exercise using your own local test traffic.

## 17. Practical Exercise 6: Generate HTTPS Traffic

HTTPS is more difficult to inspect because its application content is encrypted.

If internet access is available, run:

You can also use your browser to open the same domain.

## 19. Practical Exercise 8: Analyze TLS Filters

Show TLS traffic:

```text
tls
```

Show TLS handshake messages:

```text
tls.handshake
```

Show ClientHello messages:

```text
tls.handshake.type == 1
```

Show ServerHello messages:

```text
tls.handshake.type == 2
```

Show certificate-related handshake messages where visible:

```text
tls.handshake.type == 11
```

Show TCP port 443 traffic:

```text
tcp.port == 443
```

Show UDP port 443 traffic:

```text
udp.port == 443
```

UDP port 443 may contain QUIC/HTTP/3 traffic rather than traditional TCP-based TLS traffic.

## 20. Practical Exercise 9: Inspect TLS Certificate Information

If your capture contains a visible TLS certificate message:

1. Select the relevant packet.
2. Expand the TLS protocol section.
3. Look for certificate information.
4. Identify the certificate subject.
5. Identify the issuer.
6. Inspect validity dates if available.

Do not assume that every HTTPS capture will contain a visible certificate.

For example, TLS 1.3 encrypts certificate messages after the ServerHello, so passive captures without decryption keys may not expose them.

## 21. Understanding HTTP and HTTPS Security Risks

### A. Unencrypted HTTP

HTTP does not provide transport encryption.

Sensitive information transmitted through ordinary HTTP may be exposed to parties able to observe the network traffic.

### B. HTTPS Misconfiguration

Incorrect TLS configuration may weaken communication security.

Examples include:

- Expired certificates.
- Invalid certificate chains.
- Unsupported or weak protocol configurations.
- Incorrect hostname validation.

### C. Suspicious HTTP Requests

Unusual request patterns may indicate:

- Application malfunction.
- Automated requests.
- Web vulnerability probing.
- Unauthorized access attempts.

Investigators need context before classifying activity as malicious.

### D. Sensitive Headers

Headers such as Authorization and Cookie can contain sensitive data.

Protect packet captures and avoid sharing them publicly.

## 22. Practical Investigation Scenario

An analyst receives a capture from a local test web server.

The analyst observes:

```text
10:20:01 GET /index.html
10:20:02 HTTP 200 OK

10:20:05 GET /missing.html
10:20:05 HTTP 404 Not Found

10:20:10 HEAD /
10:20:10 HTTP 200 OK
```

Answer:

1. Which application protocol is being used?
2. What does GET do?
3. What does HTTP 200 mean?
4. What does HTTP 404 mean?
5. Why might an analyst inspect repeated requests for missing pages?
6. Does a 404 response prove that an attack occurred?

Expected reasoning:

A 404 response indicates that the requested resource was not found. It can result from ordinary user activity or application errors. It does not independently prove an attack.
