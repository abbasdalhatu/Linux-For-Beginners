## 1. Introduction

Every Linux operating system performs activities continuously.

Examples include:

- Users logging into the system.
- Applications starting and stopping.
- Services running in the background.
- Network connections being established.
- Authentication failures.
- System errors.
- Security-related events.

Linux records many of these activities in files and system logging services called **logs**.

A log is a chronological record of events generated by an operating system, application, or service.

Log analysis is the process of examining these records to understand system activity, troubleshoot problems, and identify possible security incidents.

In cybersecurity, logs are extremely important because they provide evidence of what happened on a system.

## 3. What Is a Linux Log?

A Linux log is a record of an event that occurs within the operating system or an application.

For example, when a user attempts to log in, the system may record:

```text
Nov 15 09:30:15 kali sshd[1200]: Failed password for invalid user admin from 192.0.2.50 port 50422 ssh2
```

This record contains several important details:

| Field | Meaning |
|---|---|
| Nov 15 | Event date |
| 09:30:15 | Event time |
| kali | Hostname |
| sshd | Service generating the event |
| 1200 | Process ID |
| Failed password | Event description |
| admin | Attempted username |
| 192.0.2.50 | Source IP address |

The IP address above is from a documentation-only address range and is fictional.

A security analyst can use this information to investigate unsuccessful authentication attempts.

## 4. Why Are Logs Important?

### A. Troubleshooting

Logs help administrators identify why an application or service failed.

Example:

An application crashes. Its error log may reveal the cause.

### B. Security Monitoring

Logs help identify suspicious activity.

Examples:

- Repeated failed login attempts.
- Unexpected privilege escalation.
- Unusual service activity.
- Unexpected firewall blocks.

### C. Incident Investigation

After a suspected security incident, analysts examine logs to reconstruct events.

### D. System Monitoring

Logs help administrators monitor:

- CPU-related errors.
- Storage problems.
- Hardware failures.
- Service availability.
- Application errors.

### E. Accountability

Logs can help establish which account performed an action and when it occurred.

However, logs do not always establish who was physically operating an account. Their reliability depends on configuration and integrity.

## 5. Important Linux Log Locations

Linux systems commonly store log files inside:

```bash
/var/log
```

Inspect the directory:

```bash
ls -lah /var/log
```

You may find files and directories such as:

| Log location | Purpose |
|---|---|
| `/var/log/syslog` | General system messages on some distributions |
| `/var/log/messages` | General system messages on some distributions |
| `/var/log/auth.log` | Authentication events on Debian-based systems |
| `/var/log/secure` | Authentication events on some Red Hat-based systems |
| `/var/log/kern.log` | Kernel messages on some systems |
| `/var/log/dpkg.log` | Package management activity on Debian-based systems |
| `/var/log/apt/` | APT package management logs |
| `/var/log/ufw.log` | UFW firewall logs, if configured |

Important:

Not every Linux distribution uses the same files. Some systems store most or all system events in the systemd journal.

## 6. Understanding systemd-journald

Modern Linux distributions commonly use `systemd-journald` for collecting and storing system logs.

The journal can contain events from:

- The Linux kernel.
- System services.
- Applications.
- Authentication services.
- System startup and shutdown.
- Other system components.

The main command for inspecting the journal is:

```bash
journalctl
```

Display available journal entries:

```bash
sudo journalctl
```

Display the most recent entries:

```bash
sudo journalctl -n 20
```

Display entries without opening an interactive pager:

```bash
sudo journalctl --no-pager
```

Follow new journal events in real time:

```bash
sudo journalctl -f
```

Stop real-time monitoring with:

```text
CTRL + C
```

## 8. Practical Exercise 2: Inspect System Logs

Run:

```bash
sudo journalctl -n 30 --no-pager
```

Study the output.

Look for:

- Timestamps.
- Hostnames.
- Service names.
- Process IDs.
- Information messages.
- Warnings.
- Errors.

Next, inspect the current boot:

```bash
sudo journalctl -b --no-pager
```

This displays journal entries from the current boot.

To inspect the previous boot, if its logs are available:

```bash
sudo journalctl -b -1 --no-pager
```

The previous boot may not be available if persistent journal storage is not enabled or if no earlier boot records exist.

## 9. Practical Exercise 3: Filter Logs by Priority

Linux journal messages have different priority levels.

| Priority | Name | Meaning |
|---:|---|---|
| 0 | Emergency | System is unusable |
| 1 | Alert | Immediate action required |
| 2 | Critical | Critical conditions |
| 3 | Error | Error conditions |
| 4 | Warning | Warning conditions |
| 5 | Notice | Normal but significant event |
| 6 | Informational | General information |
| 7 | Debug | Debugging information |

Display errors and more severe messages:

```bash
sudo journalctl -p err --no-pager
```

Display warnings and more severe messages:

```bash
sudo journalctl -p warning --no-pager
```

Display informational messages and more severe messages:

```bash
sudo journalctl -p info --no-pager
```

Remember: lower numeric priorities represent more severe events.

## 10. Practical Exercise 4: Inspect Logs for a Specific Service

First, identify available services:

```bash
systemctl list-units --type=service --state=running
```

Choose a service that is actually running.

For example, if NetworkManager is available:

```bash
sudo journalctl -u NetworkManager --no-pager
```

Display its latest 20 entries:

```bash
sudo journalctl -u NetworkManager -n 20 --no-pager
```

You can also inspect the SSH service if it exists:

```bash
sudo journalctl -u ssh --no-pager
```

On some distributions, the service may have a different unit name, such as `sshd`.

Do not assume a service exists simply because its name appears in an example.

## 11. Practical Exercise 5: Search Logs Using grep

The `grep` command searches text for matching patterns.

Search available text logs for the word error:

```bash
sudo grep -i "error" /var/log/syslog
```

This file may not exist on your system.

Search the current journal:

```bash
sudo journalctl --no-pager | grep -i "error"
```

Search for authentication-related events:

```bash
sudo journalctl --no-pager | grep -iE 'authentication|login|failed|accepted'
```

Explanation:

- `grep` searches text.
- `-i` ignores uppercase and lowercase differences.
- `-E` enables extended regular expressions.
- `|` allows matching any of the listed patterns.

If no results appear, record that result rather than assuming the command failed.

## 12. Practical Exercise 6: Inspect Authentication Logs

Authentication logs are especially important in cybersecurity.

They may contain information about:

- Successful logins.
- Failed logins.
- Invalid usernames.
- SSH authentication attempts.
- Sudo activity.
- Authentication service errors.

On Kali, inspect the authentication log if it exists:

```bash
sudo ls -l /var/log/auth.log
```

If available:

```bash
sudo tail -n 30 /var/log/auth.log
```

You can also inspect journal events:

```bash
sudo journalctl --no-pager | grep -iE 'sudo|sshd|login|authentication'
```

Record any authentication-related events you find.

Do not attempt to generate repeated failed logins for this exercise.

## 13. Practical Exercise 7: Understand Log Rotation

Logs can grow very large over time.

Linux systems use log rotation to manage log storage.

A rotated log may have filenames such as:

```text
syslog
syslog.1
syslog.2.gz
syslog.3.gz
```

The purpose is to:

- Prevent unlimited log growth.
- Archive older logs.
- Compress old records.
- Manage storage space.
- Maintain useful historical information.

Inspect the logrotate configuration:

```bash
ls -lah /etc/logrotate.d/
```

Inspect the main configuration:

```bash
sudo cat /etc/logrotate.conf
```

Do not execute log rotation or modify its configuration during this lab.
