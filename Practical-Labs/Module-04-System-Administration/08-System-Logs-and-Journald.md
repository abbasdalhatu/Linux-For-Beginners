## LAB 08: SYSTEM LOGS AND JOURNALD

### 1. Lab Overview

Linux systems generate logs to record events occurring within the operating system and applications.

Logs help administrators understand:

- What happened on a system.
- When an event occurred.
- Which application generated an event.
- Whether a service encountered an error.
- Whether authentication attempts succeeded or failed.
- Whether suspicious activity may have occurred.

In cybersecurity, log analysis is a fundamental part of system monitoring, incident response, and digital investigations.

For example, if a user reports that an application stopped working, an administrator can inspect the relevant logs to identify possible causes.

**Lab environment:** Kali Linux VM.

**Safety:** This lab focuses on reading and analyzing logs. Do not delete, modify, or clear system logs. Do not expose passwords, authentication tokens, or other sensitive information in your reports.

### 3. What Are System Logs?

A system log is a record of an event generated by the operating system, a service, or an application.

Examples include:

- System startup messages.
- User login events.
- Authentication failures.
- Service startup and shutdown.
- Application errors.
- Kernel messages.
- Network-related events.

Logs provide evidence that helps administrators troubleshoot and investigate system activity.

### 4. Understanding Linux Log Locations

Many Linux distributions store log files inside:

```text
/var/log/
```

Inspect the directory:

```bash
ls -lah /var/log/
```

Important log files and directories include:

| Location | Purpose |
|---|---|
| `/var/log/syslog` | General system messages on systems using rsyslog |
| `/var/log/auth.log` | Authentication and authorization events on Debian-based systems |
| `/var/log/kern.log` | Kernel-related messages where configured |
| `/var/log/dpkg.log` | Package installation and removal history |
| `/var/log/apt/` | APT package management logs |
| `/var/log/journal/` | Persistent systemd journal storage, when enabled |

Not every file exists on every Linux installation. Some systems primarily use the systemd journal.

Inspect available log files:

```bash
find /var/log -maxdepth 2 -type f
```

### 5. Understanding systemd Journal

Systemd commonly uses a logging service called journald.

Journald collects system and service messages and makes them available through:

```bash
journalctl
```

Display recent journal entries:

```bash
journalctl -n 20
```

Display the latest messages:

```bash
journalctl -e
```

Display messages from the current boot:

```bash
journalctl -b
```

Display messages from the previous boot, if available:

```bash
journalctl -b -1
```

Follow new log messages in real time:

```bash
journalctl -f
```

Exit real-time monitoring using:

```text
CTRL + C
```

### 6. Filter Logs by Time

Administrators often need to investigate events within a particular period.

Display logs from today:

```bash
journalctl --since today
```

Display logs from the last hour:

```bash
journalctl --since "1 hour ago"
```

Display logs from the last 30 minutes:

```bash
journalctl --since "30 minutes ago"
```

Display logs within a specified time range:

```bash
journalctl --since "2026-11-15 08:00:00" --until "2026-11-15 10:00:00"
```

Use the actual date and time relevant to your investigation.

### 7. Filter Logs by Priority

Journal messages have priority levels.

| Priority | Name | Meaning |
|---|---|---|
| 0 | emerg | System is unusable |
| 1 | alert | Immediate action required |
| 2 | crit | Critical condition |
| 3 | err | Error condition |
| 4 | warning | Warning condition |
| 5 | notice | Normal but significant event |
| 6 | info | Informational message |
| 7 | debug | Debugging information |

Display error messages:

```bash
journalctl -p err
```

Display warning messages and more severe priorities:

```bash
journalctl -p warning
```

Display critical messages:

```bash
journalctl -p crit
```

Display errors from the current boot:

```bash
journalctl -p err -b
```

This filtering helps reduce the amount of information an administrator must inspect.

### 8. Investigate Service Logs

System services generate logs that help administrators identify failures.

Inspect cron logs:

```bash
journalctl -u cron
```

Display recent cron messages:

```bash
journalctl -u cron -n 30
```

Inspect NetworkManager logs:

```bash
journalctl -u NetworkManager -n 30
```

Display logs from a specific service during the current boot:

```bash
journalctl -u cron -b
```

Replace `cron` with another service name when necessary.

### 9. Search Log Files Using grep

The `grep` command searches text for matching patterns.

Search for errors in a log file:

```bash
grep -i "error" /var/log/syslog
```

Search for warnings:

```bash
grep -i "warning" /var/log/syslog
```

Search for failed authentication events:

```bash
grep -i "failed" /var/log/auth.log
```

These files may not exist on your installation. If they do not exist, use the journal instead.

Search the journal for authentication-related messages:

```bash
journalctl -b | grep -iE 'authentication|failed|invalid user'
```

Display matching lines with line numbers:

```bash
grep -in "error" /var/log/syslog
```

Important options:

- `-i` – Ignore letter case.
- `-n` – Display line numbers.
- `-E` – Use extended regular expressions.

### 10. Investigate Authentication Events

Authentication logs are particularly important in cybersecurity.

They may record:

- Successful logins.
- Failed login attempts.
- Invalid usernames.
- Account authentication events.
- Privilege escalation activity.

Inspect authentication-related journal messages:

```bash
journalctl -b | grep -iE 'sudo|su|ssh|authentication'
```

Inspect the authentication log if it exists:

```bash
sudo tail -n 50 /var/log/auth.log
```

Check the current login history:

```bash
last
```

Display recent failed login records, if available:

```bash
sudo lastb
```

The availability of these records depends on your logging configuration.

**Important:** A failed login does not automatically indicate an attack. Investigate frequency, source, account, timing, and surrounding events.

### 11. Inspect Kernel Messages

The Linux kernel generates messages about hardware, drivers, devices, and system operations.

Display kernel messages:

```bash
dmesg
```

Display readable timestamps:

```bash
sudo dmesg -T
```

Display the latest 30 messages:

```bash
sudo dmesg -T | tail -n 30
```

Search for warnings:

```bash
sudo dmesg -T | grep -iE 'warning|error|failed'
```

These messages are useful when investigating:

- Device problems.
- Driver failures.
- Storage errors.
- Network interface problems.
- Hardware-related warnings.

### 12. Understand Log Rotation

Log files can grow over time.

Log rotation helps prevent logs from consuming excessive disk space.

Linux systems commonly use `logrotate`.

Inspect its configuration:

```bash
cat /etc/logrotate.conf
```

Inspect available log rotation rules:

```bash
ls -lah /etc/logrotate.d/
```

Display the installed version:

```bash
logrotate --version
```

Log rotation may involve:

- Renaming old logs.
- Creating new log files.
- Compressing archived logs.
- Removing logs after a configured retention period.

Do not execute log rotation or change its configuration during this lab.

### 13. Cybersecurity Application: Basic Log Investigation

Imagine that an administrator receives a report that an unknown user may have attempted to access a Linux system.

The administrator should investigate available evidence.

A basic investigation workflow:

**Step 1 – Identify the relevant period**

```bash
journalctl --since "1 hour ago"
```

**Step 2 – Search authentication-related events**

```bash
journalctl -b | grep -iE 'failed|invalid user|authentication'
```

**Step 3 – Inspect SSH-related messages**

```bash
journalctl -u ssh -n 50
```

The SSH service may have a different name or may not be installed.

**Step 4 – Review login history**

```bash
last
```

**Step 5 – Inspect failed login records**

```bash
sudo lastb
```

**Step 6 – Document the evidence**

Record:

- Event time.
- Event type.
- Relevant account.
- Source address, if recorded.
- Relevant service.
- Evidence source.
- Findings and limitations.

**Security principle:** Preserve original logs. Do not alter evidence during an investigation. Follow an approved evidence-handling process.

### 14. Create a Log Analysis Report Script

Create your lab directory:

```bash
mkdir -p ~/practical-labs/module04/lab08
```

Create the script:

```bash
nano ~/practical-labs/module04/lab08/log-analysis.sh
```

Enter:

```bash
#!/bin/bash

REPORT="$HOME/practical-labs/module04/lab08/log-analysis-report.txt"

{
    echo "LINUX SYSTEM LOG ANALYSIS REPORT"
    echo "================================"
    echo "Date: $(date)"
    echo "Hostname: $(hostname)"
    echo

    echo "CURRENT BOOT INFORMATION"
    journalctl --list-boots
    echo

    echo "RECENT SYSTEM LOGS"
    journalctl -n 30 --no-pager
    echo

    echo "WARNING AND ERROR MESSAGES"
    journalctl -p warning -b -n 30 --no-pager
    echo

    echo "CRON SERVICE LOGS"
    journalctl -u cron -n 20 --no-pager
    echo

    echo "AUTHENTICATION-RELATED EVENTS"
    journalctl -b --no-pager | grep -iE \
        'sudo|authentication|failed|invalid user' | tail -n 30
    echo

    echo "KERNEL MESSAGES"
    sudo dmesg -T | tail -n 20
    echo

    echo "LOG STORAGE INFORMATION"
    journalctl --disk-usage

} > "$REPORT" 2>&1

echo "Report generated: $REPORT"
```

Save the script.

Make it executable:

```bash
chmod +x ~/practical-labs/module04/lab08/log-analysis.sh
```

Execute it:

```bash
~/practical-labs/module04/lab08/log-analysis.sh
```

Read the report:

```bash
cat ~/practical-labs/module04/lab08/log-analysis-report.txt
```

The script may report missing services or unavailable log files. That is acceptable; record the limitations rather than inventing results.
